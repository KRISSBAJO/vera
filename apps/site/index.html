How Token Limits Pilot

For teams running agents with tool access

Your agent is about to do something. Should it?

Authentication says who. Authorization says what they may do. Neither answers the question an agent with shell access raises a hundred times a day. VERA answers it — and signs the answer, so the approval is bound to the exact command that runs.

Three verdicts, and a receipt for each

Every request gets a verdict, the reason codes behind it, and — when the answer is yes — a signed token bound to that exact action. These are real decisions from the system.

Verified, or asserted. Never both.

This is the distinction the whole system rests on. An agent telling VERA that the tests passed is not evidence that the tests passed.

Verified

VERA went and looked

A GitHub pull request's real approval state. Its real check runs. The migration files actually in the diff. Facts fetched under a time budget, by us, from the source.

  • Can satisfy a prerequisite
  • Carries EVIDENCE.VERIFIED
  • Absent is stated, never assumed safe
Asserted

Something told us

Anything the runtime sends: the agent's own claims, the user it says it is acting for, the environment it says it is in. Useful context. Not proof of anything.

  • Can never satisfy a prerequisite
  • Carries EVIDENCE.ASSERTED or IDENTITY.ASSERTED
  • Can raise severity, never lower it

The product is the token

An approval that is not bound to a specific action is a permission slip. VERA's token is an Ed25519 signature over a hash of the exact command, target and environment — so changing a single flag between asking and executing invalidates it.

The hash is RFC 8785 canonical JSON over a fixed field set, computed byte-identically by the service and the adapter. jti is single-use. aud names the one receiver that may spend it.

What happens in those 40 milliseconds

A real sequence, so it is numbered. Each step can refuse.

01

The adapter asks, before the tool runs

A command hook or an SDK guard hands VERA the tool, arguments, target and environment — and computes the action hash locally.

02

Evidence is gathered, under a budget

VERA fetches what it can verify itself. Anything that misses the budget is reported as EVIDENCE.MISSING — which does not satisfy a prerequisite.

03

Policy evaluates, deterministically

Cedar, not a language model. Most-restrictive-wins. A policy error becomes SYSTEM.FAIL_CLOSED, never a silent allow.

04

Baselines add severity, never remove it

Novelty, time-of-day, magnitude and burst signals can escalate a decision. They can never talk one down.

05

A human decides, if it needs one

Separation of duties excludes whoever requested the action. The reviewer sees the agent's text inside a quarantine region — it cannot impersonate VERA's own words.

06

The token is signed, spent once, and audited

The adapter re-computes the hash at execution. A mismatch is TOKEN.HASH_MISMATCH and counts as a bypass. Every signature has a matching audit event.

Two lines in the runtime you already use

The security-critical path — decide, verify the token, then run — is one shared implementation, not one per adapter.

Claude Code

A local command hook on PreToolUse / PostToolUse

# writes settings and hooks for you
npx vera-hook init \
  --endpoint https://vera.internal \
  --aud adapter:your-laptop \
  --acting-for you@example.com

# ALLOW  → runs, with a verified token
# REVIEW → holds, then allow / deny / ask
# BLOCK  → denied, with the reason shown

What VERA is not

A pilot that starts with an accurate picture is the only kind worth running. This section is in the product documentation too, word for word.

Not a sandbox

It decides; it does not contain. An agent that ignores the adapter is not stopped by VERA.

Not a runtime guarantee

A hook can be disabled. VERA raises the cost of an unreviewed action and makes it visible. It does not make it impossible.

Not an LLM judge

No model decides anything consequential. Models draft policies and summarise for reviewers; they are never the authority.

Not a compliance certificate

It produces evidence a person can use. It does not make you compliant with anything.

Not finished

The threat model lists eight accepted risks. They are accepted, not solved — and they are written down for you to read before you decide.

Thirty days, one repository, your infrastructure

Nothing leaves your network. We want the decisions VERA got wrong — the review that was obviously fine, the thing it let through that you would have wanted to see. A pilot where VERA blocked nothing and annoyed nobody is a failure, not a success.
