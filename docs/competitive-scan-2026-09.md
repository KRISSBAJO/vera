# VERA competitive landscape scan — September 2026

**Scope note.** All facts below come from 2025–2026 web sources fetched during this scan (≈75 searches/fetches). Where a claim is a vendor's own marketing (e.g. "only platform to…"), I say so. "HITL" = human-in-the-loop approval of an individual tool call at runtime (not catalog/onboarding approval). "PaC" = policy-as-code. "Behavioral" = uses cross-call/organizational history or anomaly signals, not just static rules.

**Headline verdict up front:** the *gateway + static policy + audit* layer is crowded and consolidating fast (7 acquisitions in 12 months: Natoma→Snowflake, Portkey→PANW, Astrix→Cisco, SGNL→CrowdStrike, Acuvity→Proofpoint, Lakera→Check Point, CalypsoAI→F5). *Per-call HITL held at the gateway* is now available from at least five vendors (TrueFoundry, Docker, Preloop, Peta, Delinea) plus natively in Claude Code, Codex and the OpenAI/Microsoft SDKs. What is still genuinely thin: org-specific behavioral baselines feeding the allow/review/block decision, outcome feedback loops, argument-bound expiring approvals with signed receipts, and evidence-backed reason codes — see the final section.

## 7. Deployment / infra policy gates (one paragraph)

Production deploys are already gated: **GitHub Environments** support up to six required reviewers, wait timers, self-review prevention, and (public preview) *custom deployment protection rules* that let third parties like ServiceNow or Datadog approve/deny via API ([GitHub Docs](https://docs.github.com/actions/deployment/targeting-different-environments/using-environments-for-deployment)). **OPA/Gatekeeper** and **Kyverno** enforce admission policy in Kubernetes, and native **ValidatingAdmissionPolicy** (CEL) has been GA since K8s 1.30, so cluster-level gating is commodity ([Kyverno](https://kyverno.io/docs/guides/admission-controllers/), [kubeqa](https://kubernetes.qa/blog/kyverno-vs-opa-gatekeeper/)). **HashiCorp Sentinel** gates Terraform applies inside HCP, while **Spacelift** runs Rego *approval policies* with `input.reviews` so a policy can auto-approve, reject, or return "undecided" until enough humans of the right role sign off ([Spacelift approval policy](https://docs.spacelift.io/concepts/policy/approval-policy), [PaC tools 2026](https://spacelift.io/blog/policy-as-code-tools)). Net: "policy + human approval + audit for infra change" is a solved pattern with a decade of vocabulary (Rego, Cedar, CEL); VERA should reuse that vocabulary rather than invent one, and its wedge is that these gates are blind to *agent* actors and to non-infra side effects (CRM, ERP, email, payments).

## 10. Gaps and white space (skeptical read)

**What is NOT white space (don't build the pitch on it):**
1. *"An MCP proxy that enforces policy."* ≥20 products, several OSS, plus AgentCore/Cloudflare/Snowflake. Dead.
2. *"Pause a tool call for human approval."* Native in Claude Code, Codex, OpenAI SDK, LangGraph, Microsoft AF; at the gateway in TrueFoundry, Docker (Cedar + elicitation + digest-bound confirmation), Preloop (OSS, free), Peta, Permit, Delinea, Onyx. Table stakes.
3. *"Deterministic policy-as-code for agents."* Cedar (AWS, Docker), Rego (Permit, Spacelift, Topaz), YAML (Cerbos), Polar (Oso), Colang (NeMo), Starlark (Codex). Pick one and be compatible; don't invent.
4. *"Prompt-injection / exfil / tool-poisoning detection."* Owned by PANW, Cisco, Check Point, F5, SentinelOne, Zenity, Noma, Lakera, Straiker, HiddenLayer. Buy or integrate; never compete.
5. *"Vendor bank-account fraud."* Trustpair/nsKnox/Ramp/BILL with regulator tailwind (Nacha 2026).

**Where the scan found nobody or almost nobody (VERA's plausible moat):**

| Gap | Who comes closest | Why it is still open |
|---|---|---|
| **A. Cross-call, per-organization behavioral baselines feeding the decision** (not just anomaly *alerts*) | Zenity AIDR and Noma build behavioral baselines; Lasso claims "intent" baselines; Permit fingerprints agents. | All are security-detection products producing *alerts/blocks on attack patterns*, not a business-semantic prior ("this org has never paid this vendor >$10k; this agent has never called `refund` outside business hours") that lowers or raises the review threshold. No gateway (TrueFoundry, Docker, Runlayer, Preloop) uses history at all; Claude auto-mode explicitly does not. Nobody markets "the more you run through us, the fewer approvals you need." |
| **B. Outcome feedback loops (approve/deny/rollback outcomes retrain the policy threshold)** | Orako remembers prior *answers* to avoid re-asking; gotoHuman mentions a "training dataset"; academic contextual-bandit work on approval fatigue exists; Okta recommends "progressive permission levels" as guidance. | No shipping product closes the loop from *what happened after the action* (chargeback, revert, incident, false-positive review) back into the ALLOW/REVIEW/BLOCK boundary. Approval fatigue is universally acknowledged as the failure mode ([developersdigest](https://www.developersdigest.tech/blog/approval-fatigue-agent-security-bug)) and nobody solves it with data. |
| **C. Evidence-backed reason codes** (a decision object that cites *which* policy rule, *which* behavioral deviation, *which* external evidence — e.g. account-validation result — produced REVIEW) | Cerbos returns deny reasons to the agent; Noma surfaces "full risk context" in its review queue; Codex/Claude show reasons in UI. | Nothing produces a structured, machine-readable, auditor-grade reason code set comparable to card-network decline codes. Reviewers in every product above see "agent X wants to call Y" plus raw args. |
| **D. Payload-bound, expiring approvals with a signed callback/receipt** | **Docker** binds the confirmation to a request digest (closest); **Pipelock** emits Ed25519-signed decision receipts; **Authensor** hash-chains its ledger; **Google AP2** signs cart/payment mandates (consumer checkout only); Stripe SPT is scoped/expiring but is a payment token, not a decision. TrueFoundry approvals are explicitly *not* bound to arguments and time-boxed grants skip re-review. | No general-purpose product combines (i) approval cryptographically bound to the exact tool + normalized arguments, (ii) TTL/one-shot semantics, (iii) a signed decision token the *downstream* system (or a second gateway) can verify offline, and (iv) delivery as a webhook the agent runtime consumes. Docker has (i) but only in-session; Pipelock has (iii) but for egress scanning; AP2 has all four but only for cards. This is buildable and defensible *if* VERA publishes a verifiable format and gets one or two SaaS/ERP receivers to verify it. |
| **E. Vendor-agnostic MCP proxy + PaC + human review + risk signals together, sold to the app/platform team as an API rather than to the CISO as a platform** | Preloop (OSS) has proxy + PaC + review but no risk; Onyx has review + risk but is a CISO platform w/o PaC; Permit has PaC + review + weak risk; Delinea is PAM-buyer-shaped. | The combination exists in fragments. The honest caveat: this is a *packaging* gap, not a technology gap, and it is the easiest for an incumbent (Cloudflare WriteGuard adding approvals, TrueFoundry adding risk, Anthropic shipping a hosted approval queue) to close within two quarters. Treat E as the wedge, A–D as the moat. |
| **F. Second-party reviewer semantics** (finance/security/manager approves, not the end user) with separation of duties and self-approval prevention | GitHub environments have "prevent self-review"; Spacelift has role-counted approvals; CrewAI/gotoHuman route to teams. Auth0 CIBA and Docker elicitation ask the *same* user/session that triggered the action. | Agent-native products almost all ask the *operator*, which is the wrong reviewer for consequential business actions. SoD-aware routing (n-of-m, role, amount thresholds, no self-approval) copied from CI/CD and IaC into the agent tool-call path is not on any agent-gateway feature list found. |

**Positioning implication.** The scan supports VERA as a *decision service* (signed ALLOW/REVIEW/BLOCK with reason codes, org baselines, outcome learning) that is consumed *through* the crowded layer — as a Claude Code HTTP hook, an OpenAI `needsApproval` function, a Cedar/OPA external data source, a TrueFoundry/Preloop/agentgateway policy plugin, and a GitHub custom deployment protection rule — rather than as yet another proxy competing on being in the path. Being "in the execution path" is necessary for the data moat but is not itself differentiating in September 2026; the org-specific history and the verifiable decision artifact are.

**Biggest threats, ranked:** (1) Anthropic/OpenAI shipping a hosted approval queue + org policy on top of hooks/`needsApproval`; (2) Cloudflare extending WriteGuard tiers into approvals + behavioral scoring on its traffic corpus; (3) Onyx (well funded, already routes to humans, already reads reasoning) moving down-market to a developer API; (4) Preloop/OSS commoditizing the proxy+approval layer at $0.
